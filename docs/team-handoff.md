# 轻务 Qingwu：团队对齐、现状与分工

更新日期：2026-09-17

本文给 2–3 人开发团队提供共同基线。第一次团队会议应一起阅读本文，并在文末的负责人表中填入真实姓名或 GitHub 用户名。

## 1. 一句话共识

轻务不是聊天机器人、课程表，也不是学校管理后台。它是一款面向团支书、班委、学生会和社团成员的 Windows 个人事务工作台：一项学生工作只录入一次事实，随后用同一份事实驱动通知、提醒、推文、待办、材料检查和最终归档。

最重要的产品原则是：

1. 事实准确优先于文案好看。
2. AI 是可选加速器，不是运行前提。
3. 用户必须确认 AI 提取的事实和生成的文案。
4. 数据默认留在本机，不自动发送消息，不自动发布内容。
5. v0.1.0 先完成单机小闭环，不扩张到账号、云同步和多人审批。

### 2.3 尚未完成的发布门槛

- Python 3.12 正式 sidecar 和 CLI 构建。
- Rust 编译和 Tauri 桌面联调。
- 干净 Windows 10/11 x64 安装与卸载测试。
- 真实 OpenAI 请求测试；测试材料必须是虚构数据。
- 至少 6 名目标用户试用。
- 至少 3 次活动组织、3 次材料收集、2 次报销整理。
- GitHub、npm、PyPI、域名和商标的完整同名检查。

因此，当前仓库应称为“v0.1.0 开发实现基线”，不能称为“v0.1.0 已发布”。

## 3. 当前最主要的风险

按优先级排序：

### P0：桌面壳尚未完成运行与打包验证

Rust/Tauri 源码已经在 GitHub Windows runner 通过 `cargo check`，但静态编译通过不等于桌面应用可正常运行。第一优先级仍是让至少一台开发机完成 `tauri dev`、真实 sidecar 通信、托盘和通知验证。出现桌面主链路问题时，暂停新增产品功能，先修通主链路。

### P0：测试数量仍少

现有测试覆盖了核心机制，但不足以覆盖发布清单中的全部边界。尤其需要补充数据库迁移、AI 异常、归档路径穿越、报销组、草稿锁定、相对日期、时区和文件占用测试。

### P0：冻结产物不是正式产物

本机验证 EXE 来自 Python 3.11；项目要求 Python 3.12。打包脚本已经会拒绝非 3.12 解释器，但还需在 3.12 环境重新构建。

### P1：前端目前重在流程完整，尚未经过用户试用

界面能覆盖所有模块，但“用户能否在 5 分钟内完成第一版通知”还没有数据。不要仅凭团队成员熟悉产品后的操作速度判断易用性。

### P1：AI 接口需要受控实测

不能只测试成功请求。至少要验证无 Key、错误 Key、断网、超时、限流、模型不存在、返回结构错误和敏感样本预览取消。

### P2：功能扩张风险

暂不增加云同步、多人协作、微信读取、自动发送、自动发布、在线收集页和学校系统集成。任何新想法先进入 Issue，不直接插入 v0.1.0。

## 4. 推荐分工

### 三人方案

| 角色 | 主要所有权 | 日常交付 | 不单独决定的事项 |
| --- | --- | --- | --- |
| `wjgheh`：产品与前端 | 用户流程、React、视觉、事务模板、文案体验、用户测试 | 页面、交互、模板、可用性记录、用户反馈整理 | 数据结构、隐私边界、发布范围 |
| `URNR0`：核心与 AI | Python、SQLite、事实/草稿版本、AI Provider、材料和归档 | 核心接口、自动测试、AI 失败降级、迁移方案 | UI 最终形态、自动化高风险行为 |
| `Caspian315`：桌面与质量 | Rust/Tauri、Credential Manager、通知、托盘、PyInstaller、CI、安装包 | 桌面联调、构建流水线、发布包、系统测试和安全审查 | 产品范围、关键事实语义 |

三人不是各写各的。每个 PR 至少由另一个角色审查：

- A 的流程变更请 B 或 C 检查数据和系统后果。
- B 的核心规则请 A 检查是否符合真实学生工作语言。
- C 的权限、通知和打包变更请 B 检查数据边界，A 检查用户提示。

### 两人方案

| 角色 | 主要所有权 | 次要所有权 |
| --- | --- | --- |
| A：产品与体验 | React、交互、模板、文案、用户研究、文档 | 端到端场景测试、Issue 管理 |
| B：核心与平台 | Python、SQLite、AI、材料、归档、Rust/Tauri、CI 和发布 | 安全、性能、安装测试 |

两人方案中，桌面平台工作容易全部压到 B 身上，因此每周固定安排一次 2 小时结对联调：A 负责按真实用户路径操作和记录问题，B 负责日志与修复。测试夹具、发布清单和最终放行必须共同确认。

### 如果第三人只能兼职

不要让兼职成员接手需要持续上下文的数据库或事实版本核心。更适合分配：

- Windows 干净机器测试。
- 文档、截图和演示视频。
- 三个事务模板的真实案例 fixture。
- 用户访谈、问题复现和回归测试。
- 安装包、中文路径和不同电脑环境的兼容性记录。

## 5. 从现在开始的八周计划

原计划的代码骨架已经提前形成，后续八周应从“堆功能”转为“理解、联调、补测和真实试用”。

### 第 1 周：所有人跑通同一基线

- 每人克隆仓库并阅读 README、本文、架构和隐私文档。
- 安装 Node.js、Python 3.12、Rust stable 和 WebView2。
- 跑通 `python -m pytest`、`npm test`、`npm run build`、`cargo check`。
- 至少一台机器跑通 `npm run tauri dev`。
- 三人分别讲解一次前端、Python、Rust 数据流，避免只有一个人懂整体。
- 把所有失败记录为可复现 Issue，不在群聊里只发一句“运行不了”。

验收：所有成员都能说明一次 `affair.create` 从 React 到 SQLite 的完整路径，至少两台电脑通过基础检查。

### 第 2 周：打通 Windows 桌面闭环

- 修完 Rust 编译和 Tauri 权限问题。
- 验证 sidecar 启动、退出和异常提示。
- 验证 Credential Manager 保存、读取、替换和删除 Key。
- 验证关闭到托盘和“完全退出后停止提醒”。
- 生成第一份开发版 NSIS/MSI。

验收：一台未安装 Python 的 Windows 机器能创建事务、生成离线通知并导出 ZIP。

### 第 3 周：事实与文案正确性

- 补相对日期、冲突地点、缺失事实和重新确认测试。
- 补草稿锁定、版本比较、恢复旧版本和定向过期测试。
- 使用虚构数据实测 OpenAI 成功、超时、限流和非法结构。
- 检查 AI 失败后离线模板仍可使用。

验收：关键事实不被模型改写；事实变化能稳定使相关草稿过期；无 Key 和断网能完成通知闭环。

### 第 4 周：材料、报销与归档可靠性

- 补报销重复项目、票据缺失和金额字段测试。
- 测试中文路径、长路径、重名文件、文件占用、移动和修改。
- 测试归档路径穿越、输出冲突和磁盘空间不足。
- 人工解压并核对 ZIP、HTML、PDF、DOCX 和 manifest。

验收：归档包和清单一致，源文件未被修改，敏感字段与绝对路径不进入归档。

### 第 5 周：时间线与 Windows 提醒

- 测试 24 小时、2 小时、到期提醒。
- 测试重启、休眠恢复、修改截止时间和提前完成待办。
- 测试通知权限被拒绝和开机启动关闭。
- 观察是否出现提醒堆叠、漏提醒或重复提醒。

验收：记录完整的提醒测试矩阵；重复提醒问题清零，完全退出提示明确。

### 第 6 周：可用性和真实语言

- 邀请 2–3 名非开发者做预试用。
- 从真实但已脱敏的上级通知开始计时。
- 记录首次通知生成耗时、回退次数、看不懂的按钮和修改次数。
- 优先修流程阻断和事实错误，再修视觉细节。

验收：多数新用户能在 5 分钟内生成首版通知；阻断问题都有 Issue 和负责人。

### 第 7 周：目标用户正式试用

- 扩展到至少 6 人，覆盖团支书、班委和社团成员。
- 完成 3 次活动组织、3 次材料收集、2 次报销整理。
- 每次记录输入、输出、耗时、错误、修改次数和是否愿意继续用。
- 冻结新功能，只修 P0/P1 问题。

验收：达到发布清单中的真实用户数量和事务数量；不存在未处理的阻断问题。

### 第 8 周：发布候选与 v0.1.0

- 完成名称、域名和商标检查。
- 在干净 Windows 10/11 x64 机器安装、升级、卸载。
- 生成 NSIS、MSI、便携包、CLI 和 SHA-256。
- 完成 CHANGELOG、安装说明、已知问题和隐私说明。
- 创建 `v0.1.0-rc.1`，观察后再决定是否标记 `v0.1.0`。

验收：发布检查清单全部勾选；所有成员共同批准 Release。

## 6. GitHub 协作规则

### 分支

- `main`：随时保持可测试，不直接写功能。
- `feat/<短名称>`：新功能，例如 `feat/reminder-permission`。
- `fix/<短名称>`：错误修复，例如 `fix/archive-confirmed-facts`。
- `docs/<短名称>`：文档和示例。
- `test/<短名称>`：测试与 fixture。

### Issue

每项超过 30 分钟的工作先建 Issue，至少写清：

- 为什么要做。
- 用户场景或错误复现。
- 明确不做什么。
- 验收方法。
- 负责人和优先级。

优先级统一为：

- `P0`：主流程不可用、事实错误、数据/隐私风险、无法构建。
- `P1`：严重影响效率或发布质量，但存在绕过方式。
- `P2`：体验改进和非阻断优化。
- `P3`：未来想法，不进入当前里程碑。

### Pull Request

- 一个 PR 只解决一个明确问题。
- PR 关联 Issue，并写出验证命令和结果。
- 行为变化必须新增或修改测试。
- 不提交真实姓名、学号、手机号、票据、聊天记录或 API Key。
- 至少一人审查后再合并；修改事实规则、归档或凭据处理时必须两人共同确认。
- 合并前至少通过 Python、前端、构建和 Rust CI。

### 提交信息

推荐使用：

```text
feat: add reminder permission state
fix: export only confirmed facts
test: cover conflicting locations
docs: clarify Windows build steps
```

## 7. 每周协作节奏

- 周初 20 分钟：从里程碑选择本周 Issue，每人最多同时进行 1 个主要任务。
- 开发中：在 Issue 留可复现进展，不依赖聊天记录保存关键决定。
- PR 前：作者自行跑测试并填写 PR 清单。
- 周中 30 分钟：演示真实可运行增量，不只汇报写了多少代码。
- 周末 30 分钟：更新发布清单、风险和下周优先级。
- 重要决策：写入文档或 Issue 的 Decision 记录，不能只在口头达成。

## 8. Definition of Done

一个任务只有同时满足以下条件才算完成：

- 功能或修复符合 Issue 验收条件。
- 有自动测试，或明确记录无法自动化的人工测试步骤。
- 不破坏离线降级路径。
- 不扩大敏感数据上传范围。
- 用户提示使用自然、明确的中文。
- 相关文档和 CHANGELOG 已更新。
- PR 已审查，CI 已通过。
- 对需要 Windows 的功能，至少有一份真实桌面验证记录。

“代码写完了”“在我的电脑上能打开”“AI 看起来回答正确”都不等于完成。
